## Current Checkpoint

OS는 19개, Networking은 29개 개념 + 1개 총정리, Database는 24개 개념 + 1개 총정리, Runtime & Concurrency는 15개 개념 + 1개 총정리, System Design은 10개 주제까지 준비되었습니다. 문서 생성 자체는 학습 완료 증거가 아닙니다.

System Design 두 번째 묶음에서는 다음을 자료 없이 설명할 수 있어야 합니다.

1. Database Scaling은 Read/Write pattern, peak load, query latency, hot row, storage growth를 먼저 측정하고 병목에 맞게 확장한다.
2. Read Replica는 read throughput을 늘릴 수 있지만 replication lag과 stale read 때문에 read-after-write routing을 별도로 고려해야 한다.
3. Write Scaling은 read scaling보다 어렵고 transaction 최적화, batching, queue, partitioning, sharding을 trade-off와 함께 검토한다.
4. App Horizontal Scaling 시 `instance count × DB pool size`가 DB capacity를 넘지 않는지 확인한다.
5. CAP의 핵심은 network partition 상황에서 consistency와 availability를 동시에 완벽히 보장할 수 없다는 것이며 단순히 평소 세 항목 중 두 개를 고르는 문제가 아니다.
6. Strong / Eventual / Read-after-write Consistency는 데이터와 operation별 요구사항에 따라 다르게 선택할 수 있다.
7. Eventual Consistency를 선택하면 retry, deduplication, ordering, reconciliation과 중간 상태 UX까지 설계해야 한다.
8. Distributed Idempotency는 ambiguous timeout과 retry로 같은 operation이 반복되어도 side effect가 중복되지 않게 만드는 설계다.
9. Idempotency Key는 UNIQUE Constraint나 conditional insert 같은 atomic ownership과 request payload 검증이 함께 필요하다.
10. At-least-once message delivery에서는 consumer idempotency가 필요하며 Idempotency와 Distributed Lock은 해결하는 문제가 다르다.
11. Rate Limiting은 quota/fairness/downstream 보호를 위해 사용하며 Token Bucket은 burst capacity와 장기 refill rate를 분리할 수 있다.
12. 여러 App Instance의 local counter만으로는 global rate limit이 깨질 수 있으므로 distributed coordination이나 gateway가 필요하다.
13. Rate Limiting, Backpressure, Load Shedding은 모두 보호 장치지만 quota 정책, 처리 능력 피드백, 실제 과부하 대응이라는 서로 다른 역할을 가진다.
14. Distributed Lock은 process-local lock과 달리 여러 instance를 조정하지만 먼저 DB constraint, conditional update, optimistic locking 같은 단순한 대안을 검토해야 한다.
15. Lease/TTL 기반 Distributed Lock에서는 stale owner가 다시 작업할 수 있으므로 중요한 side effect에는 fencing token 같은 보호가 필요할 수 있다.
16. Distributed Lock은 transaction이나 exactly-once를 자동 제공하지 않으므로 idempotency와 failure recovery를 별도로 설계한다.
