# 08. HTTP/1.1

## 이번 학습 목표

- HTTP 요청/응답 구조를 설명한다.
- Keep-Alive와 Connection reuse가 왜 중요한지 설명한다.
- HTTP/1.1의 Head-of-Line Blocking과 여러 TCP 연결 사용 배경을 이해한다.

---

## 1. HTTP는 무엇인가?

HTTP는 Application Layer의 request-response 프로토콜입니다.

```text
Client
  ↓ Request
Server
  ↑ Response
```

HTTP/1.1은 일반적으로 TCP 위에서 동작합니다.

---

## 2. 요청 구조

예:

```http
GET /users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
Connection: keep-alive
```

구성:

- Method
- Request target
- HTTP version
- Headers
- optional Body

응답도 Status Line, Headers, Body 구조를 가집니다.

---

## 3. TCP Connection을 매번 새로 만들면?

각 요청마다 새 TCP 연결을 만들면 다음 비용이 생길 수 있습니다.

```text
DNS (필요 시)
TCP handshake
TLS handshake (HTTPS)
HTTP request
response
connection close
```

그래서 연결을 재사용하면 handshake 비용을 여러 요청에 분산할 수 있습니다.

HTTP/1.1에서는 persistent connection이 기본 동작입니다.

---

## 4. Keep-Alive

Keep-Alive는 같은 TCP connection에서 여러 HTTP 요청을 처리하도록 해줍니다.

```text
TCP connection
├─ Request 1 / Response 1
├─ Request 2 / Response 2
└─ Request 3 / Response 3
```

백엔드에서는 `HttpClient` 같은 객체와 connection pool을 올바르게 재사용하는 것이 중요한 이유입니다.

연결을 지나치게 자주 만들면:

- handshake 증가
- TIME_WAIT 증가
- ephemeral port pressure
- CPU 비용 증가

등이 생길 수 있습니다.

---

## 5. HTTP/1.1 Pipelining

HTTP/1.1에는 여러 요청을 응답을 기다리지 않고 연속으로 보내는 pipelining 개념이 있습니다.

```text
Request A
Request B
Request C
   ↓
Response A
Response B
Response C
```

하지만 응답 순서를 요청 순서대로 유지해야 하므로 앞 응답이 늦어지면 뒤 응답도 막힐 수 있습니다.

이것이 HTTP/1.1 수준의 Head-of-Line(HOL) Blocking 문제입니다.

실무에서는 pipelining이 널리 활용되지 않았고, 브라우저는 여러 TCP connection을 병렬로 열어 한계를 완화하는 방식을 많이 사용했습니다.

---

## 6. 여러 TCP Connection의 비용

여러 연결을 만들면 동시에 여러 리소스를 가져올 수 있지만:

- TCP handshake 수 증가
- TLS session 비용
- Socket / FD / kernel state 증가
- Congestion window가 연결마다 따로 존재

라는 비용도 있습니다.

HTTP/2는 이 문제를 한 연결에서 여러 stream을 multiplexing하는 방향으로 개선합니다.

---

## 7. Content-Length와 Chunked Transfer

HTTP는 body의 끝을 알아야 합니다.

대표적인 방법:

- `Content-Length`
- chunked transfer encoding
- connection close (상황에 따라)

HTTP/1.1의 persistent connection에서는 message framing을 정확히 아는 것이 특히 중요합니다.

---

## 8. Stateless의 의미

HTTP를 stateless protocol이라고 부르는 것은 각 요청을 처리하기 위해 프로토콜 자체가 이전 요청의 애플리케이션 상태를 반드시 기억해야 하는 것은 아니라는 의미입니다.

하지만 실제 서비스는:

- Cookie
- Session
- Token
- DB state

등으로 사용자 상태를 유지할 수 있습니다.

따라서 “HTTP가 stateless라서 서버는 상태를 저장할 수 없다”는 설명은 틀립니다.

---

## 9. Backend에서 중요한 관점

- Connection pool 재사용
- Timeout 설정
- Retry 정책
- Idempotency
- Header size
- Request body size
- Proxy와 Keep-Alive 설정

특히 외부 API 호출마다 새 `HttpClient`/connection을 만드는 패턴은 connection churn을 키울 수 있습니다.

---

## 10. 60초 면접 답변

> HTTP/1.1은 일반적으로 TCP 위에서 동작하는 request-response 프로토콜입니다. persistent connection을 기본으로 사용해 하나의 TCP 연결을 여러 요청에 재사용할 수 있고, 이를 통해 TCP나 TLS handshake 비용을 줄입니다. HTTP/1.1에는 pipelining이 있지만 응답 순서를 유지해야 해서 앞선 응답이 늦으면 뒤 응답이 막히는 HOL blocking 문제가 있습니다. 이를 완화하기 위해 여러 TCP 연결을 사용하는 방식이 쓰였지만 연결별 비용이 증가합니다. HTTP/2는 하나의 연결에서 여러 stream을 multiplexing해 이 부분을 크게 개선합니다.

---

## 핵심 요약

```text
HTTP/1.1 = request/response over persistent TCP
Keep-Alive = connection reuse
HTTP/1.1 pipelining → application-level HOL blocking
```
